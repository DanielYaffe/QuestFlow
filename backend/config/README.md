# RunPod manifest

Model availability is a **build-time** property now. Each style is its own RunPod serverless
endpoint with its own Docker image and one baked-in checkpoint; there is no ComfyUI API to ask what
is installed. `manifest.json` is that answer, generated by `build.sh` and shipped as app config.

The backend loads it once at boot (`src/config/manifest.ts`), logs the version, and validates every
style and generation request against it — an unknown checkpoint or LoRA is a 400 from us rather than
a job we paid a GPU cold start for.

## Files

| File | Committed | Purpose |
|---|---|---|
| `manifest.example.json` | yes | Template. Documents the shape. |
| `manifest.local.json` | yes | Points the three endpoint keys at models in a local ComfyUI, for use with the local shim. |
| `manifest.json` | **no** (gitignored) | The real thing, with real endpoint IDs. Copy from the example and fill in. |

## Setup

```sh
cp config/manifest.example.json config/manifest.json
# then replace every REPLACE_WITH_RUNPOD_ENDPOINT_ID with the real endpoint ID
```

`endpoint_id` may not be null or empty — the schema rejects it, so the backend fails to boot rather
than discovering the problem on the first generation. `build.sh` emits `null` because endpoints do
not exist until they are created by hand, so filling them in is a required step.

In production, prefer hosting the manifest and setting `RUNPOD_MANIFEST_URL`; the file here is the
fallback that keeps a flaky bucket from stopping the backend from starting.

## Local development

Run the shim, which translates RunPod's protocol to your local ComfyUI:

```sh
npm run shim
```

then set these in your local environment file:

```
RUNPOD_API_BASE=http://localhost:8787
RUNPOD_MANIFEST_FALLBACK_PATH=config/manifest.local.json
RUNPOD_MANIFEST_URL=
```

`manifest.local.json` deliberately keeps the three production endpoint keys so style validation
behaves the same locally; only the checkpoint and LoRA filenames differ, and all three resolve to
the same ComfyUI.

## When models change

1. Rebuild and push the image with a new tag.
2. Update the image tag on that RunPod endpoint.
3. Regenerate `manifest.json`.
4. Deploy it.

Steps 3 and 4 are the ones that get forgotten — a backend on an old manifest rejects LoRAs that
exist and accepts ones that do not. `POST /admin/manifest/reload` re-reads it without a redeploy,
and the version is visible in the admin header.
